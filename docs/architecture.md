├──────────────────────────────────────────────────────────────────┤
│ Ядро planner/                                                   │
│  fleet ─ sensors ─ wind ─ energy                                │
│  coverage ─ dubins/turns ─ avoid ─ mission                      │

## Компоненты

| Модуль | Назначение |
|---|---|
| `data/fleet.yaml` | Датасет бортов и нагрузок: значения из паспортов со ссылкой на источник, допущения помечены в `assumed` |
| `planner/fleet.py` | Загрузка и валидация датасета (pydantic) |
| `planner/sensors.py` | Высота, полоса, шаг галсов, скорость по типу съёмки |
| `planner/wind.py`, `energy.py` | Треугольник скоростей, бюджет вылета |
| `planner/coverage.py` | Галсы, выбор направления, клеточная декомпозиция |
| `planner/dubins.py`, `turns.py` | Развороты самолёта (пути Дубинса) и мультиротора |
| `planner/avoid.py` | Граф видимости для обхода NFZ и границы разрешённой зоны |
| `planner/mission.py` | Порядок галсов, нарезка на вылеты, уход на площадки |
| `planner/partition.py`, `grid_partition.py` | Разбиение области между бортами: полосами и с учётом дальности |
| `planner/planner.py` | Оркестрация, критерии, балансировка, локальный поиск, проверки |
| `planner/pareto.py` | Фронт Парето (параллельно в процессах) |
| `planner/geodata.py` | Разбор данных заказчика (KML): зоны ограничений с высотами и временем, высотные препятствия, задания на съёмку |
| `planner/advisor.py` | Советник: кривая «время работ от числа бортов», ответы про срок и число бортов |
| `data/geodata/*.geojson` | Выгрузки заказчика в нашем формате (341 зона, 5162 и 3201 препятствие, 696 участков задания) |
| `planner/terrain.py` | Рельеф Copernicus DEM GLO-30 |
| `planner/export.py` | GeoJSON и KML для каждого борта, ZIP со всеми заданиями |
| `api/main.py` | HTTP API; раздача собранного интерфейса |
| `frontend/src/` | Интерфейс: `App.tsx`, `MapView.tsx`, `charts.tsx`, `api.ts` |

## Поток данных

1. Пользователь рисует или загружает сценарий: область, разрешённая зона, NFZ, ВПП, резервные площадки, парк, тип съёмки, ветер, критерий.
2. Интерфейс отправляет `PlanRequest` на `POST /api/plan` (или `/api/pareto`).
3. Ядро строит план (см. [algorithm.md](algorithm.md)), сохраняет его в памяти процесса под `plan_id` и возвращает `PlanResponse`: сводку, планы бортов с вылетами и участками, исключённые борта, предупреждения.
4. Интерфейс рисует маршруты, график вылетов и фронт Парето; файлы заданий скачиваются по `plan_id`.

## Технологии

- Backend: Python 3.12, FastAPI, pydantic 2, shapely 2 (GEOS), pyproj, networkx, numpy, rasterio, simplekml.
- Frontend: React 19, TypeScript, Vite, Leaflet, leaflet-geoman.
- Развёртывание: один Docker-контейнер (API + статика интерфейса), рельеф демо-районов вшит при сборке.
- Внешние сервисы и ключи: не требуются. Подложка — OpenStreetMap (с атрибуцией по Tile Usage Policy); рельеф — открытый бакет Copernicus DEM на AWS, без ключа.

## Решения и почему

- **Эвристики вместо точного решателя.** Задача (покрытие + маршрутизация + распределение по разнородному парку с ветром) NP-трудная. Разбиение полосами/сеткой с балансировкой по фактическому времени даёт план для 100 км² за секунды и допускает интерактивное сравнение вариантов.
- **Оценка по фактическому плану.** Доли бортов подбираются по времени реально построенных вылетов (с разворотами, ветром, обходами и сменой АКБ), а не по упрощённой модели.
- **Хранение планов в памяти.** Для демо и одиночного пользователя достаточно; PostGIS по ТЗ необязателен.
