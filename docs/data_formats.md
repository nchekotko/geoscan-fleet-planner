# Форматы данных о воздушном пространстве

Заказчик выложил примеры данных и отдельно попросил: «В файле нет стандартного формата записи
данных о диапазоне высот и времени действия ограничения. Предложите свой». Здесь — что пришло,
как мы это читаем и какой формат предлагаем.

## Что выдал заказчик

| Файл | Что внутри | Объектов |
|---|---|---|
| `Границы полетов.kml` | пример задания на съёмку: полигоны участков (`clampToGround`, атрибут `FID`) | 696 |
| `Московская зона.kml` | временные и постоянные запретные зоны: `name` (индекс зоны), `description` и `ExtendedData` с полями `Name`, `Altitudes`, `Type` | 341 |
| `obstacles_Московская область.kml` | высотные препятствия 3D-примитивами: полигон или линия, высота — третья координата, `extrude`, `altitudeMode` | 5162 |
| `высотные препятствия Приморский край.kml` | то же по Приморскому краю | 3201 |

Ссылка на выгрузку: <https://disk.360.yandex.ru/d/HjUEBhOJAzMAaw> (чат задачи, 22–23.09.2026).
Файлы в репозиторий не добавлены (10 МБ исходников); в репозитории лежит разобранная
выгрузка `backend/data/geodata/*.geojson`, её делает `backend/data/convert_geodata.py`.

Что в данных заказчика сложного:

- **Высоты — свободным текстом.** 176 различных формулировок на 341 зону: «От земли до 500 м
  (1700 фут) AMSL», «От FL280 до FL400», «От 800 м (2700 фут) AMSL до FL90», «На всех высотах»,
  «От земли до 450 м (1500 фут) AGL», пустая строка.
- **В той же строке — оговорки:** «Некорректная геометрия! От земли до 1850 м (6100 фут) AMSL»,
  «…Исключая границы района аэродрома Киржач в период…», «Не распространяется на воздушные
  суда, выполняющие полеты (перелеты) под ли…» (текст обрезан в источнике).
- **Времени действия нет вообще**, хотя 137 зон из 341 помечены как временные (`врем_ограничение`).
- **Отсчёт высоты смешанный**: `AMSL` (над уровнем моря), `AGL` (над землёй), `FL` (эшелон по
  стандартному давлению), «от земли».
- **У препятствий отсчёт высоты задан `altitudeMode`** и встречается опечатка
  (`relativeToSeaFloor` вместо `absolute`) — 2612 объектов из 5162 в московском файле.

## Предлагаемый формат

За основу взят GeoJSON (RFC 7946, WGS84, lon/lat) — он уже используется в API сервиса, читается
любым ГИС-инструментом и легко валидируется. Ограничение или препятствие — `Feature`, разобранные
поля лежат в `properties`. Исходная строка сохраняется в `alt.raw`, оговорки — в `notes`: ничего
из данных не теряется, и решение всегда можно проверить против источника.

### Зона ограничения

```json
{
  "type": "Feature",
  "geometry": { "type": "Polygon", "coordinates": [[[37.5, 55.6], "…"]] },
  "properties": {
    "kind": "restriction",
    "id": "UUR201",
    "name": "UUR201",
    "zone_type": "temporary",
    "alt": {
      "lower_m": 800.0, "lower_ref": "AMSL",
      "upper_m": 2743.2, "upper_ref": "AMSL",
      "raw": "Некорректная геометрия! От 800 м (2700 фут) AMSL до FL90"
    },
    "active": {
      "from": "2026-09-29T06:00:00+03:00",
      "to": "2026-09-29T18:00:00+03:00",
      "daily": ["08:00", "20:00"],
      "raw": "ежедневно 08:00–20:00 МСК"
    },
    "notes": "Некорректная геометрия!",
    "source": "Московская зона.kml"
  }
}
```

| Поле | Значение |
|---|---|
| `kind` | `restriction` |
| `id`, `name` | индекс зоны из источника (`UUR201`), человеческое название |
| `zone_type` | `prohibited` (запретная зона), `permanent` (постоянное ограничение), `temporary` (временное), `special` (особый режим), `unknown` |
| `alt.lower_m`, `alt.upper_m` | границы в метрах; `upper_m: null` — «на всех высотах» (без верхней границы) |
| `alt.lower_ref`, `alt.upper_ref` | отсчёт: `GND` (от земли), `AGL` (над рельефом), `AMSL` (над уровнем моря). Эшелоны `FL` переводятся в метры `AMSL` по стандартному давлению: FL090 = 9000 фут = 2743,2 м |
| `alt.raw` | исходная строка из данных заказчика |
| `active.from`, `active.to` | начало и конец действия, ISO 8601 с часовым поясом; отсутствуют — действует всегда |
| `active.daily` | суточный интервал `["ЧЧ:ММ", "ЧЧ:ММ"]` (можно через полночь: `["22:00", "06:00"]`) |
| `notes` | оговорки из источника, которые не относятся к высотам |
| `source` | имя исходного файла |

Почему так:

- **Две границы с собственным отсчётом**, а не одна высота: в данных заказчика встречается
  «от земли до 500 м AMSL» — низ и верх в разных системах отсчёта, свести их к одной без рельефа
  нельзя.
- **`upper_m: null` вместо большого числа**: «на всех высотах» — это отсутствие границы, а не
  «до 10 000 м».
- **Время — два независимых механизма**: интервал (`from`/`to`) для NOTAM-подобных ограничений и
  суточное окно (`daily`) для режимов вида «ежедневно с 08:00 до 20:00». Оба необязательны.
- **`raw` и `notes` обязательны к сохранению**: разбор свободного текста не бывает полным, и
  оператор должен видеть исходную формулировку (в интерфейсе она выводится в попапе зоны).

### Высотное препятствие

```json
{
  "type": "Feature",
  "geometry": { "type": "Polygon", "coordinates": [[[35.6025, 56.4536], "…"]] },
  "properties": {
    "kind": "obstacle",
    "id": "UUWV100069",
    "obstacle_type": "COMMUNICATION_TOWER",
    "top_m": 77.1,
    "top_ref": "AGL",
    "source": "obstacles_Московская область.kml"
  }
}
```

| Поле | Значение |
|---|---|
| `kind` | `obstacle` |
| `id` | индекс препятствия из источника (`UUWV100069`) |
| `obstacle_type` | `COMMUNICATION_TOWER`, `BUILDING`, `VEGETATION`, `TREE`, `CHIMNEY`, `ANTENNA`, `POWER_TRANSMISSION_PYLON`, `LIGHT_SUPPORT_STRUCTURE`, `FENCE`, `NAVAID`, `SIGN`, `URBAN`, `CONSTRUCTION`, `UNKNOWN` (префикс `OTHER:` из источника отбрасывается) |
| `top_m` | верх препятствия в метрах |
| `top_ref` | `AGL` (над землёй, `altitudeMode = relativeToGround`) или `AMSL` (над уровнем моря, `absolute`) |
| `top_agl_m` | добавляется сервисом в ответе: верх в метрах над землёй области съёмки |

Геометрия — `Polygon`/`MultiPolygon` (мачты, здания, лес), `LineString`/`MultiLineString` (ЛЭП)
или `Point`. Высота в третьей координате KML сохраняется в `top_m`, поэтому 2D-геометрии
достаточно: горизонтальный габарит плюс верхняя отметка.

### Задание на съёмку

```json
{ "type": "Feature", "geometry": { "type": "Polygon", "coordinates": "…" },
  "properties": { "kind": "survey_area", "id": "1491" } }
```

Несколько участков в одном задании допустимы: сервис принимает `MultiPolygon` как область съёмки
и планирует их вместе (границы между участками не удлиняют галсы сильнее, чем границы одного).

## Как сервис это использует

1. **Зона мешает не всегда.** Полоса высот работ считается по парку: от самой низкой высоты
   съёмки до самой высокой плюс эшелоны перелёта (в ответе — `airspace.alt_band_agl_m`). Зона
   попадает в расчёт, только если её полоса высот пересекает полосу работ и она действует в окно
   работ (`mission_start` + `mission_window_h`). Пример: зона «от 800 м AMSL до FL90» съёмке на
   150 м над землёй не мешает; зона «от земли до 500 м AMSL» — мешает. Остальные зоны возвращаются
   с `applies: false` и `skip_reason`, чтобы оператор видел, что они учтены и почему пропущены.
2. **AMSL → над землёй по рельефу.** Высота земли берётся из Copernicus DEM GLO-30 по области
   (`airspace.ground_min_m`, `ground_max_m`). Перевод консервативный: нижняя граница зоны — по
   самой высокой земле участка, верхняя — по самой низкой. Так зона скорее попадёт в расчёт, чем
   будет пропущена. Без рельефа высота земли принимается за 0 м, и об этом выдаётся
   предупреждение.
3. **Препятствие — либо перелетаем, либо облетаем.** Если верх препятствия с вертикальным
   зазором (`obstacle_clearance_m`, по умолчанию 30 м) ниже высоты съёмки, оно не мешает. Если
   выше — подняться над ним нельзя, не потеряв заданный GSD, поэтому препятствие с горизонтальным
   зазором (`obstacle_buffer_m`, по умолчанию 50 м) становится запретной зоной: маршруты его
   обходят, а неснятая площадь попадает в покрытие и в предупреждения.
4. **Фильтр по коридору работ.** Зоны и препятствия дальше 2 км от области и баз не
   рассматриваются: выгрузка на регион содержит тысячи объектов, а мешают единицы.

## Импорт

- `POST /api/import/kml` с телом `{"kml": "<содержимое файла>", "kind": "auto"}` разбирает KML
  заказчика и возвращает `Feature` в описанном формате. `kind`: `auto` (определяется по признакам
  файла), `zones`, `obstacles`, `task`.
- `GET /api/geodata` перечисляет выгрузки, лежащие рядом с сервисом
  (`backend/data/geodata/*.geojson`), `GET /api/geodata/{name}` отдаёт выгрузку целиком.
- В интерфейсе то же доступно кнопками «Импорт KML/GeoJSON» и «Данные о воздушном пространстве».
- Программно: `backend/planner/geodata.py` (`parse_zones_kml`, `parse_obstacles_kml`,
  `parse_task_kml`, `parse_alt_band`), разбор высот покрыт тестами в
  `backend/tests/test_geodata.py`.

## Ограничения разбора

- Оговорки вида «Исключая границы района аэродрома Киржач в период…» сохраняются текстом, но
  геометрию и время из них сервис не извлекает: такие исключения нужно задавать отдельными
  объектами.
- Пометка «Некорректная геометрия!» из данных заказчика остаётся в `notes`; геометрия при этом
  берётся как есть (самопересечения исправляются `make_valid`).
- Время действия в выданных файлах отсутствует, поэтому в сценарии `moscow_real.json` временные
  зоны заданы без окна и считаются действующими всегда. Формат готов принять окно, как только
  источник его даст.
